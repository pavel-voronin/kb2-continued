# Модульные тесты

Тестируется только `continued`: её собственные правила и согласованное поведение. Оригинальная игра и ветка `main` не используются как эталон и не участвуют в проверках. При исправлениях и развитии меняются соответствующие тесты; остальные защищают от непреднамеренных изменений.

Стенд для `continued` исполняет код Turbo Pascal 7.0. Для каждого модуля собирается отдельная программа с прямым вызовом его процедур. Соседние модули заменяются явно заданными заглушками. Состояние, память, файлы и очередь ввода восстанавливаются перед каждым тестом. Полное прохождение игры не запускается.

Игровые файлы в `SRC/` не изменяются. Метки покрытия и доступ к закрытым процедурам добавляются только в рабочие копии. Компилятор берётся из `PASCAL/`, ресурсы для фикстур собираются из `SRC/ART/*.PCX` исходным `RSPACK.PAS`. Готовая оригинальная игра и сборки поисковика не нужны.

## Запуск

Нужны Python 3.11 или новее и DOSBox-X. В PowerShell из корня:

```powershell
python -m venv .git/kb2-unit-host
.git/kb2-unit-host/Scripts/python.exe -m pip install -r TEST/HOST/requirements.txt
$env:KB2_DOSBOX = 'C:\path\to\dosbox-x.exe'
TEST/UNIT.ps1 -Python .git/kb2-unit-host/Scripts/python.exe
```

Проверить выбранные модули:

```powershell
TEST/UNIT.ps1 -Python .git/kb2-unit-host/Scripts/python.exe -Module KBECON,KBPLAYER
```

Обычный запуск требует успешных тестов и полного покрытия достижимых точек Pascal, инструкций ASM и обоих исходов условных переходов ASM выбранных модулей. Непокрытая точка без проверенного обоснования недостижимости завершает проверку с ошибкой. `-RequireComplete` оставлен как явное указание того же требования. Для разработки отдельных тестов есть `HOST/run.py --allow-coverage-gaps`.

Рабочая папка — `.git/kb2-test/UNIT/`; её можно перенести переменной `KB2_TEST_WORK`. Там создаются:

- `RESULT.json` — результаты тестов и точные непокрытые точки;
- `COVERAGE.html` — отчёт по модулям и исходным строкам;
- `JUNIT.xml` — результаты для CI;
- `ASSEMBLY/` — перечень исходных инструкций ASM в машинном коде;
- `CACHE/` — сохранённые успешные результаты с покрытием.

Кеш учитывает машинный код, ресурсы, реализацию стенда, конкретный тест и его ожидания. Добавление теста не запускает заново остальные неизменившиеся тесты. Устаревшая сборка после изменения `SRC/` не принимается. Сборки и вычисления ограничены двумя логическими процессорами с пониженным приоритетом в Windows.

## Что проверяется

Для арифметики, памяти, PCX и графических примитивов используются независимые проверки результата. Для команд и меню фиксируются изменения игрового состояния и таблиц существ, результаты функций, конечное состояние генератора случайных чисел, изменения файлов, графические плоскости EGA, звуковые команды и вызовы зависимостей. Аргументы-строки сохраняются в момент вызова, до повторного использования памяти Pascal.

Ожидания находятся в `EXPECT/`. Это текущее поведение, включая известные ошибки, а не описание идеальных правил. Именованные примеры ошибок находятся в `HOST/bugs.py`. При исправлении правила следует отдельно изменить его тест и проверить причину расхождения.

Обычный запуск не обновляет ожидания. Режим `HOST/run.py --record` добавляет отсутствующие ожидания для текущей `continued`; существующие значения он не заменяет. Новые ожидания и изменения тестов проверяются вместе с изменениями правил.

Покрытие измеряется по выполненным операторам, входам в процедуры, исходам условий, циклов и `case`. Инструкции ASM и исходы условных переходов измеряются отдельно. Декларации данных проверяются размерами записей и отдельными проверками таблиц. Синтетический `case-unmatched` показывает отсутствие подходящей ветви.

В исходной базе выполнены 7 796 из 7 824 точек Pascal (99,64%). Остальные 28 точек имеют обоснования недостижимости в `UNREACHABLE.json`: например, выход из `until false` или ветка вне диапазона результата `Random`. Это 100% достижимых точек, а не утверждение о выполнении всех ветвей. Отдельно выполнены все 1 304 инструкции ASM и все 192 исхода условных переходов ASM.

Каждое обоснование связано с точными токенами модуля, формой точки и компилятором. Изменение исходника делает его устаревшим; фактическое выполнение исключённой точки также считается ошибкой стенда. Причины и оставшиеся пробелы видны в HTML. Проверки этих ограничений, инструментирования и кеша запускаются перед игровыми тестами. Покрытие не доказывает проверку всех сочетаний входных данных или точность аппаратной эмуляции.

`HOST/hardware.py` реализует плоскости, защёлки и регистры EGA для графических unit-тестов. Его вывод сверялся с отдельной программой в DOSBox-X: 112 000 байт четырёх плоскостей совпали. Этот тест относится к адаптеру стенда; unit-исполнение не предназначено для измерения аппаратных тактов.

Составные сценарии находятся в `SCENARIOS/`: четыре кампании с генерацией и сохранением/загрузкой, 16 200 ударов, 112 поисков соседней цели, 20 выборов отряда и 12 фаз ИИ. Они компилируются с настоящими игровыми модулями и исполняются в DOSBox-X после модульных тестов при полном запуске `UNIT.ps1`. Ожидания в `EXPECT/SCENARIOS.JSON` зафиксированы по текущей continued, без обращения к классике. Отдельный запуск: `python TEST/HOST/scenarios.py`. Успешные неизменившиеся сценарии берутся из кеша. При выборе `-Module` запускаются только модульные тесты.
